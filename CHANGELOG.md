# Changelog

## v0.1.11

- The Devices view checks whether a device is reachable only while the view is visible, every 60 s (was 15 s, always), once right when it opens, and not for devices with a running session. It stops after the window has been unfocused for 5 minutes. This stops the constant connections that made the phone's sshd fork, log and wake from suspend.

## v0.1.10

- Device agent 1.10.8 makes each mirror frame cheaper on the phone: libvpx encodes with up to 4 threads (3 before) and one token partition per thread, and the full-size screen conversion has a vectorisable path (about twice as fast in a host benchmark, identical picture). Expected on the Jolla Phone (8 cores): encode about 10 % and convert about half faster; not yet measured on a phone. A faster encoder speed was tried and rejected: it sent 2 to 5 times the target bitrate.
- Device agent 1.10.8 paces 60 fps mirroring at the fastest step the phone really keeps: the per-frame cost now includes the capture cycle (the compositor fills one request per display frame, so the Jolla Phone's 17 ms readback takes two), and the pace settles at 30 fps there instead of aiming at 45 or 60 and delivering about 35 unevenly. Host simulation only; not yet measured on a phone.
- Mirror details: `Frame rate … (phone paces N)` now shows the pace the phone keeps (60, 45, 30, …), not the requested rate.

## v0.1.9

- Faster mirror and a frame rate limit on the phone: device agent 1.10.7 adds **Frame rate limit** (30 or 60 fps, default 30, kept across upgrades) to Settings › System › Developer agent › Mirror. VS Code now asks for 60 fps and the phone caps it (older agents keep 30); the pace then steps through 60, 45, 30, 20, 15, 10 and 7.5 fps as the phone keeps up. Changing the limit while the mirror runs restarts it like the Idle mode switch (`Connecting… mirroring is restarting`, the Settings page shows `Restarting mirroring…`). The agent now captures the next screen picture while it encodes the current one (two capture buffers) and asks for it earlier when the compositor's readback is slow; before, every frame whose readback took longer than half a frame slot waited half a slot more than needed, which on the Jolla Phone held the mirror at about 13.5 fps with 15 ms of phone time per frame. Mirror details gain `Stages` (per captured frame: hold, capture, readback, convert, encode and send, in ms), `Captured` (new screen pictures per second, without re-encodes of a still screen) and `Frame rate limit`. Older agents send no stages and the rows stay hidden. With a 60 fps limit, adaptive quality still judges the phone's encode time against 30 fps, since the agent first lowers the frame rate. Not yet verified on the emulator or a phone.
- `Uninstall Device Agent` leaves nothing of the agent on the device. It first stops the device's mirror, device logs and app monitor, then removes the package as before and, for older agents too, the agent's settings folder, an RPM copy older versions left in `/tmp`, the service's `multi-user.target.wants` link and failed state. As the device user it then removes a socket folder or staged screenshots a crashed agent left, `~/.cache/sailfish-tools`, closes notifications lipstick still lists for the agent, and checks read-only that no package, file, process or D-Bus name of the agent is left. One notification says what was removed and names anything still there. The SDK tools (`rsync`, `sdk-deploy-rpm`, `gdb-gdbserver`) are not touched. The RPM is now copied to the extension's private folder `~/.cache/sailfish-tools` (mode 0700) instead of `/tmp`, so nothing else can replace it before it is installed as root, and an install cancelled at the password prompt removes the copy. Not yet verified on the emulator or a phone.
- Installing, updating or removing the agent closes a running Settings app (only it, never the home screen), so the Developer agent page appears or disappears the next time Settings opens. If it still shows the old state, **Restart Home Screen** in the install or uninstall notification restarts the home screen after a confirmation (`Restart the home screen on "<device>"? Running apps will close.`); it is never done automatically. The install, upgrade and removal notifications now ask whether to restart the home screen and say what stays stale if you do not.
- New `Restart Home Screen` action (Devices view right-click menu on hardware devices and running emulators, and the Command Palette): runs `systemctl --user restart lipstick` as the normal SSH user, so it needs no root and no password. It replaces `Restart Phone Session…`, which needed the developer-mode password.
- Device agent 1.10.1: the package's erase scriptlets also remove a socket folder or staged screenshots a crashed daemon left, the old `systemctl enable` link and the failed state, and close the Settings app; the daemon removes staged screenshots and closes its notifications when it stops (the start notice shows a banner once per installation and comes back silently on the next start). The package now ships its own boot link instead of `systemctl enable` writing one to `/etc` (the old link is removed on upgrade). Upgrades still keep the settings. No protocol change.
- Device agent 1.10.2: log and stats streams end with `developer mode is off` within 3 s of Developer Mode being turned off (before, only new requests were refused); a `journalctl` that cannot start ends the log stream with one error line instead of leaving it silent; lipstick's screenshot call no longer blocks the agent (it gives up after 3 s and fails only that capture); `--request` judges the reply's status on its whole first line even when it arrives in pieces; a text mirror request with `"lease":0` gets no lease (binary and VP8 streams always have one); the stats stream rechecks the app's known pid instead of scanning `/proc` every tick. Not yet verified on the emulator or a phone.
- Virtual keypad for keypad phones: with device agent 1.10.3 on a phone with a hardware keypad (for example the Commodore Callback), the mirror shows the phone's keys under the picture (digits, `*`, `#`, the arrows and OK, Menu, Back, Call and the F21–F23 function keys, only those the phone has). Clicking a button presses that key on the phone, under the same focus lease, phone `Allow control` switch, rate limit and indicator as taps; the PC keyboard is not forwarded. The layout is the user's own: when the phone reports a keypad and the workspace has no layout for its model, the strip shows `Keypad detected` with **Create layout**, which saves a starter built from the keys the phone reports (default `.sailfish/keypads/<model>.json`) and opens it; the keypad appears once a layout exists and reloads when the file is saved. Picking an existing valid layout file uses it without rewriting it (an invalid one is overwritten only after asking). A broken edit shows one error and keeps the last good layout; a missing file shows `Keypad layout missing` with **Edit** (the path stays remembered). The strip hint is the lowest-priority warning and goes away once you use it. `Sailfish: Edit Keypad Layout` opens it again and `Sailfish: Reset Keypad Layout` forgets it without deleting the file. No layout is bundled. Not yet verified on the emulator or a phone.
- Device agent 1.10.3: `ping` reports `keypad` (the model from `/etc/hw-release` and the whitelisted keys the keypad really has) and `key` in `mirrorInput`, only on a phone with a hardware keypad; the mirror accepts press and release of one whitelisted key. No text, power, volume or arbitrary key codes.
- Touch indicator on more phones: with device agent 1.10.4 the phone's `Show touch indicator` switch works on compositors that offer only `alien_manager` v1 (for example the Jolla Phone on Sailfish OS 5.2), and when the phone cannot draw the marker at all, the mirror draws it over the picture instead (it fades out on release). Mirror details show `Touch indicator: on phone`, `in mirror` or `off`. The marker appears only while the phone switch, control and the input lease are on, follows only touches sent from VS Code, and disappears at once on blur, control off or stream end. Not yet verified on the emulator or a phone.
- Device agent 1.10.4: binds `alien_manager` v1 or v2 for the touch overlay, adds `touchIndicatorPath` to the mirror's phone-settings message and sends `contact` records (native coordinates of the agent's own injected touches) only when the marker must be drawn in the mirror.
- Idle mode switch on the phone: device agent 1.10.6 adds **Idle mode** to Settings › System › Developer agent (default on, kept across upgrades). On, a still screen goes idle as before (sharpening frames, then `idle` in the strip). Off, the agent keeps encoding and sending frames at the current pace while the screen does not change, never reports idle, and the strip never says `idle`. A blank phone display sends nothing in either mode. Changing the switch while the mirror runs restarts the mirror: the agent ends the stream with `restarting: idle mode changed on the phone`, the panel shows `Connecting… mirroring is restarting` and connects once more, and the Settings page shows `Restarting mirroring…` and disables **Idle mode** and **Allow screen view** until the new stream is up (10 s at most; the agent refuses both changes meanwhile). The mirror details show `Idle mode: on` or `off`. This replaces the earlier VS Code setting `sailfish.mirror.idleStreaming` and its `"idle":"pause"` request field, which are removed (they were never released). With agent 1.10.5 and later the first change after an idle screen is shown at the full frame rate at once instead of speeding up in steps. Not yet verified on the emulator or a phone.
- The mirror never falls back to screenshots any more. With device agent 1.10.5 a phone whose native screen recorder cannot be used ends the stream with `native screen capture unavailable: <reason>` (the panel shows Disconnected with **Reconnect**, and the Sailfish OS output channel and the phone's journal give the reason); a recorder that breaks mid-stream is reopened up to 3 times in 5 seconds first. The `Screenshot capture` warning and the `screenshot (<why>)` details row are gone; `Take Screenshot` is unchanged.

## v0.1.8

- New **Device Monitor** tab per device (`Open Device Monitor`, also from the Devices view, the status bar tooltip and Debug, which opens it beside the editor unless `sailfish.debug.openDeviceMonitor` is off). It is one narrow column: the connection (dot, Connected or Offline, `Wi-Fi · aarch64 · OS 5.1.0.11 · agent 1.10.0`) and the app card (name, pid, mode, CPU and memory with small line graphs, uptime, restarts, crashes; or `<app> not running`). The actions are icon buttons in the tab's title bar: Restart app and Stop app (only while the app runs), Screenshot, Mirror and Show logs. New settings `sailfish.monitor.pollIntervalSeconds` and `sailfish.monitor.logLines`.
- `Show Device Logs` and the monitor's **Show logs** stream the device journal into the one `Sailfish Device Log` output channel: JSON lines with level, pid and tag (`13:42:01.123 W 4321 harbour-demo: message`) with agent 1.10.0, plain text with older agents, ANSI colours removed, refusals from the phone as one line. Cancel the progress notification, or choose Stop when running the command again, to end it; a device switch stops it too. Logs still need the device agent.
- App stats: process id, CPU, memory, uptime, restarts and crashes of the launched app, every second with agent 1.10.0 and every 5 seconds through `sfdk` without it.
- Device agent 1.10.0: `logs` can stream `journalctl` output as JSON (`"format":"json"`) and resume after a cursor (`"after"`), `ping` reports `logFormats` and `stats`, and the new `stats` stream reports an app's CPU, memory and start/exit events. Older agents keep working with plain text logs and polled stats. Not yet verified on a phone.
- Fixed: `Install Deploy & Debug Tools on Device` spun forever on a device that could not be reached. When the read-only check could not run, it fell back to installing all three packages, asked for the password and started `devel-su` over a connection that never came up; Cancel stopped `sfdk` but not the `ssh` it had started, so the notification stayed open. Now the device's SSH port is probed first (3 s) and an unreachable device gets `Sailfish: "<device>" is offline — connect it (USB or Wi-Fi, Developer Mode on) and try again.` with **Open Devices view** and **Retry**, before any password is asked for. A check that could not run (timeout after 20 s, connection refused, `ssh` exit 255) never installs anything; only a check that ran but printed something unexpected still installs all three. The install says what it waits for (`connecting to "<device>"…`, `checking the developer-mode password…`, `refreshing repositories 40%`, `downloading…`), stops with a clear message when the device does not prompt within 30 s, stays silent for 3 minutes, drops the connection, refuses the password or runs past 10 minutes, and Cancel kills `sfdk` with everything it started and closes the notification. Debug on Device's gdbserver check, and installing or removing the device agent, use the same offline check. A cancelled or timed-out `sfdk` run no longer waits for pipes a leftover `ssh` keeps open. Not yet verified on a phone.
- A build that fails because rpmbuild cannot find a file listed in `%files` now says which one: `Packaging failed: the spec lists /usr/libexec/... in %files, but the build did not install it. Check the %files section and the INSTALLS in the .pro` (up to three paths, then `and N more`) instead of only showing the raw `File not found` lines.

## v0.1.7

- Fixed: Restart (Ctrl+Shift+F5) in a session started by Debug on Device or Debug Installed App failed. The C/C++ extension cannot restart a session itself, so VS Code ends it and launches the same configuration again 300 ms later; sfdk's `gdbserver --once` had already exited when the first GDB disconnected, and the extension also treated the end as Stop and cleaned up, so the new GDB found nothing to connect to. The extension now tells Restart from Stop (VS Code sends `disconnect`/`terminate` with `restart: true`), kills what is left of the app, starts gdbserver again in the same "<app> (debug)" terminal and keeps the session registered; GDB retries its connection for up to 30 s (`set tcp auto-retry on`, `set tcp connect-timeout 30`) while gdbserver starts. Stop cleans up as before, and if VS Code does not relaunch within 20 s or gdbserver cannot be started again, everything is stopped. Restart does not build or deploy; use Debug again to run changed code. A gdbserver that no GDB ever connected to is now also killed on the device by its exact command line. Not yet verified on the emulator or a phone.
- Fixed: Debug on Device and Debug Installed App failed to launch with the C/C++ extension 1.34 (`Specified argument was out of the range of valid values. (Parameter 'arch')`). The debug configuration now sets `targetArchitecture` from the target (`x86`, `arm`, `arm64`). Verified on the emulator (breakpoint, step, variables). If starting the debug session throws, gdbserver is now stopped on the device instead of being left running.
- Debug builds are now really unoptimised. `sfdk build -d` alone still compiled with `-O2` (the `%qmake5` macro passes the platform's `%optflags`), so breakpoints moved and stepping showed stale values. For build type Debug the extension now also passes `-- --define '__global_cflags -O0 -g -pipe -Wall -fexceptions -fstack-protector --param=ssp-buffer-size=4 -Wformat -Wformat-security'` to `sfdk build`: the compiler gets `-O0 -g` with the target's own architecture flags, and `-D_FORTIFY_SOURCE=2` (which needs optimisation) is left out. No change to the `.pro` or `.spec` is needed; Release builds are unchanged, `QT_NO_DEBUG` stays defined, and `sailfish.build.extraArgs` still come last. Because qmake does not rebuild objects when only the flags change, Build, Deploy, Run and Debug first run `sfdk make -- clean` when the project's `Makefile` was generated for the other build type. Verified in the Sailfish platform SDK container (5.1.0.11, i486, armv7hl, aarch64): compile lines and `DW_AT_producer` show `-O0`, the debuginfo packages and rpmlint result are as before. Not yet verified through the SDK's own `sfdk` and build engine.
- Deploying with the SDK method waits for you to confirm the installation on the device screen; the progress notification now says `confirm the installation on the device screen…`, and declining reports `Sailfish: the installation was declined or not confirmed on the device`. Running a command right after activation no longer says "no Sailfish project found" while the project is still being detected.
- New **Build** view at the top of the Sailfish sidebar (shown for a Sailfish project). It lists the project (folder name, `.pro` file), Target, Device (with connected / offline / not registered), Type, Deploy, Signing and Last build; a click on a row opens its picker (the last-build row opens the `Sailfish OS Build` channel). Last build reads `⟳ Building… 1:15 · deploying` while a build runs (build task, Run, Debug and Deploy all report to it), then `✓ succeeded 14:03 · 47s` or `✗ failed 2 min ago · 4.0s`. The title bar has Build (`$(tools)`, replaced by Stop while a build runs, new commands `Stop Build` and `Show Build Log`) and the ⋯ menu groups Clean Project Build, Rebuild, Package, Validate RPM (new command `Validate RPM`), Run / Debug Installed App, Set Up Package Signing and Show Build Log.
- New `Clean Project Build`: a deep clean of what an in-source build generates in the project folder, done on the host (no sfdk): Makefiles written by qmake (hand-written ones are kept), `*.o`, `moc_*.cpp`, `qrc_*.cpp`, `*.moc`, `.qmake.stash`, the `OBJECTS_DIR` / `MOC_DIR` / `RCC_DIR` / `UI_DIR` directories and `TARGET` binaries named in those Makefiles, and the `RPMS`, `BUILD`, `BUILDROOT` directories. A modal lists the counts and the first paths before anything is deleted; every deleted path is logged in the Sailfish OS channel. It never follows a symlink, never leaves the project folder and never touches `.git`. A committed generated Makefile is deleted too, since it makes the build skip qmake. `Rebuild` runs it and then Build, and a failed build's notification offers **Clean & Rebuild**. `Clean` is unchanged.
- The Emulators and Devices views are one **Devices** view with two groups, Emulators and Devices; the title bar has Add Device, Install available Emulator (a picker of the emulators you can install) and Refresh. The sidebar order is Build, Devices, SDK.
- Run, Debug and Deploy show their build log live. Every stdout/stderr line of the engine start, `sfdk build` and `sfdk deploy` streams into a new `Sailfish OS Build` output channel, cleared at the start of each build and revealed without taking focus (set `sailfish.build.revealLog` to `false` to stream without revealing). Engine-side paths are rewritten to host paths like in the build task, each step has a header and a `build finished (exit N, Xs)` / `deploy finished …` line, and **Show output** on a build or deploy failure notification opens this channel.
- Active device sessions are visible. While something runs on the selected device, its status bar item shows `$(debug)` on the warning background for a debug session (`$(pulse)` for an app, log stream or mirror), and its tooltip lists what runs and how to stop it; the Debug button reads `Debugging…`. In the Devices view the device's description lists the sessions (`● connected · debugging · device logs`) and an inline stop button appears only for devices with sessions. The new command `Stop Sessions on Device` (selected device, or the tree item) stops them all and shows the same notice as a device switch.
- Changing the selected device (status bar, `Set Default Device`, or editing `sailfish.device`) first stops whatever still runs on the old device, then switches: the debug session and its gdbserver, app terminals started by Run / Run Installed App (the app stops, the terminal closes), the device log stream and, once the mirror registers with the new session registry, the mirror panel. There is no prompt. A short notice lists what was stopped (`Stopped on "<old>": debugging, <app>, device logs. Now using "<new>".`) with a **Show output** action, each stop is logged in the Sailfish OS channel, and a session that fails or takes longer than 10 s to stop is named in the notice but never blocks the switch. Editing `sailfish.device` directly cleans up right after the change.
- The phone's own settings (device agent 1.9.0, Settings → System → Developer agent) win over VS Code. `Device Agent Status` shows what the phone allows (screen view, control, logs, session indicator, muted notifications, touch indicator). Screenshots and device logs say plainly when the phone has turned screen view or logs off, or stopped the session (`screen view disabled on the phone`, `logs disabled on the phone`, `stopped from the phone`), and the log request tells the phone which host it comes from. Older agents are unaffected.
- The mirror panel's status strip is one short line again: a coloured dot, `Live` and the frame rate (`30 fps`, or `idle`), at most one warning (`Slow path`, `Reduced for phone`, `Reduced for link`, `Screenshot capture` or `N dropped`, in that order of priority), then a `Control` or `Control off on phone` pill, **Reconnect** or **Update agent** when they help, and an ⓘ button. The button opens a **Mirror details** popover (close with ×, Escape or a click outside) with the transport, codec and size, received kbit/s, frame rate, latency, phone time, capture path, dropped frames and control state, and **Copy details** copies them as text. The Sailfish OS output channel still logs the long form on every change.
- The screen mirror follows the phone's settings too (agent 1.9.0): the status strip shows a `Control off on phone` pill (the details and the Sailfish OS output say `disabled on the phone`) and input stops at once when the phone turns control off, and a mirror the phone ends reads `screen view is disabled on the phone` or `stopped from the phone`. The mirror also tells the phone which host it comes from. The agent now advertises press, move and release (`down`, `move`, `up`) next to tap and swipe.
- `Install Deploy & Debug Tools on Device` checks first and installs only what is missing. A read-only check (no password) looks for `rsync`, `sdk-deploy-rpm` and `gdbserver`; if all are present it says so and stops, otherwise it names the missing ones, asks for the password once and installs only those packages (if the check fails it installs all three as before). The install's output now streams into the Sailfish OS output channel and the progress notification shows the current step (refreshing, downloading, installing) with a percent when `pkcon` prints one. Debug on Device uses the same check, so a missing gdbserver installs only `gdb-gdbserver`.
- The mirror is interactive with device agent 1.7.0: click the displayed phone screen to tap and drag to swipe. Native recorder frames and touchscreen events use the phone panel's fixed coordinates, independent of the encoded image size and display rotation. Control is capability-gated and opt-in, works over both the SSH forward and the SDK fallback, and older agents remain view-only. Screenshot fallback is deliberately view-only because Lipstick does not expose the top-window rotation it applies to saved screenshots.
- Remote input has its own short focus lease. VS Code renews it only while the mirror panel and VS Code window are focused, and sends an immediate stop on blur, hide, close, disconnect or transport replacement; the agent releases a contact and cancels control after three seconds without renewal. Both sides validate every message and use rolling rate limits; the agent rechecks Developer Mode on activation and stream renewal. Only taps and one-finger swipes are supported—there is no keyboard, text, power-button or arbitrary input path.
- Device agent 1.6.0 adds VP8 video over the binary forward. The panel decodes it with WebCodecs and automatically stays on JPEG when VP8 is unavailable. Video raises the ceiling to 30 fps at 720 px/2000 kbit/s, requests key frames after reload or decoder loss, drops raw captures rather than encoded delta frames when behind, and adapts bitrate and width to the link.
- A steadier mirror frame rate with device agent 1.8.1. The phone now paces video frames on an even clock instead of following the compositor's timing. Only when the phone clearly cannot encode at the requested rate for two seconds does it step down to a lower steady rate (20, 15, 10 or 7.5 fps), one step at a time, and it steps back up when there is time again, also trying the faster rate every 10 seconds. (Agent 1.8.0, never released, stepped down at 85 % of the frame time, jumped several steps at once and came back up only with a lot of room: a few slow seconds at the start of a stream, such as while the phone shows its "Screen is being viewed" banner, left the Jolla Phone at 7.5 fps where about 30 ms per frame allows close to 30.) The colour conversion is spread over several cores and the VP8 encoder runs at a fixed real-time speed that holds the target bitrate; there is no longer a key frame burst every 10 seconds. Adaptive quality now tells a slow phone from a slow link. It lowers only the width when the encoder cannot keep up, shown as `Reduced for phone` in the strip, keeps full width while the encoder keeps up, and needs two seconds of slow frames before acting, so short spikes no longer change the level. The strip's frame rate is smoothed, and a still screen reads `idle` instead of a falling frame rate; the last picture is re-encoded once or twice after the screen stops changing, so it sharpens. On the emulator, conversion is 2–3 times faster, and on a loaded emulator the stream stays at 720 px and 2000 kbit/s where it used to drop to 540 px and 800 kbit/s. Phone numbers are not measured yet.
- `Mirror Device Screen` is much faster and lighter on the phone. When the device's key is registered, the mirror streams over an SSH port forward as binary frames (no base64, no helper process per stream) instead of going through the SDK connection. If the forward cannot be set up, it falls back to the previous path automatically, and the panel strip says `Slow path`, and the mirror details (the ⓘ button) and the output channel give the reason (`SDK connection (ssh forward unavailable — <reason>)`). The extension acknowledges each frame, so the phone never gets more than two image frames or four video frames ahead of the PC.
- The phone captures the screen through Lipstick's own recorder instead of taking a screenshot per frame. There are no "Screenshot captured." notices while mirroring, and the phone does less work per frame. If the recorder is unavailable (an older Lipstick, or access refused), the agent falls back to screenshots and the mirror still works, only slower and with the notices. Measured on the emulator: about 4 frames per second at the default rate (about 2 before), a frame time of about 20 ms (about 260 ms before) and a round-trip latency around 35 ms. Nothing is measured on a phone yet.
- Adaptive quality: on a weak link the mirror keeps its frame rate and lowers the image width and JPEG quality step by step, then raises them again when the link recovers. The strip shows `Reduced for link` while the quality is below what was requested; the mirror details show the size and quality of the current image. It needs the forward transport; the fallback path does not adapt. Measured on the emulator with a throttled link: 4 frames per second held while the link was limited, where it was 1 to 1.6 before.
- The mirror is lease-based: VS Code renews it every 20 seconds while the panel is visible, and the phone stops streaming by itself 60 seconds after the last renewal, whatever happened on the PC or the link. If that happens, the panel shows `disconnected` with a Reconnect button.
- The extension keeps its own known-hosts file for the forward and pins the device's host key. On first use the key is read through the SDK connection, not trusted blindly. A changed key is refused: an emulator is re-pinned automatically, and for a phone VS Code warns and offers **Trust New Key**; until then the mirror uses the SDK connection.
- The phone shows one on-phone indicator while the screen is being viewed ("Screen is being viewed from VS Code") and changes it to "Screen is being controlled from VS Code" while focused input is active. Control stays disabled until the notification service confirms that controlled state, and remains disabled if the indicator cannot be shown. It is a single entry that is reused, shows a banner only for meaningful security transitions and goes away shortly after the stream ends. The "Developer agent is running" notice no longer piles up on every agent start, and it now mentions screen viewing and control.
- Device agent 1.8.1 (1.2.0 added the binary encoding, acknowledgements, the lease and `ping` fields; 1.3.0 native capture; 1.4.0 adaptive quality; 1.5.0 capture-path reporting; 1.6.0 VP8; 1.7.0 focused tap/swipe input; 1.8.0 frame pacing and idle-screen reporting; 1.8.1 the corrected pacing). Existing requests remain compatible, so an older extension works with the new agent and the new extension works with older agents through view-only fallbacks. Installing or upgrading the agent restarts it, so a running log stream ends and the phone's start notice is updated in place. An open mirror panel instead shows `connecting: the agent is being updated` and connects again once by itself when the new agent answers (it used to show `disconnected: connection closed`, and pressing Reconnect then started a second stream that the update replaced a second later). The agent package requires Wayland and libvpx runtime libraries.
- An outdated device agent is no longer used silently. If the agent on the device is older than the one this extension includes, `Mirror Device Screen` still opens but shows a notification once per device per session with an **Update Device Agent** action (which installs and reconnects the mirror), and the panel strip says `Slow path` with an **Update agent** button (the details name the old agent: `agent 1.1.0 — update for the fast mirror`). `Device Agent Status` shows the same note and action.
- With device agent 1.5.0 or newer, each frame reports how it was captured, and the mirror details show `Capture: native recorder` or `screenshot (<why>)` (the strip shows `Screenshot capture` as its warning); the Sailfish OS output channel logs each change of capture path. Older agents report nothing and the details show nothing extra.

## v0.1.4

- A **Deploy** button in the status bar (build and deploy, without launching), next to Build, Run and Debug.
- `Sailfish: Run Installed App` and `Sailfish: Debug Installed App` launch or debug the app already on the device, without building or deploying again. If the app is not installed there, they offer to build and deploy first.
- Fix installing tools on the device (`Install on device`, `Install Deploy & Debug Tools on Device`): `devel-su` now gets a terminal. A single `-t` gave it none when VS Code starts sfdk, which ended in "Remote process crashed".

## v0.1.3

- Detect the app's native binary when `%files` lists the bare `%{_bindir}` directory (the stock Sailfish app template) or `%{_bindir}/*`, not only `%{_bindir}/<name>`. Run and Debug had launched such C++ apps with `sailfish-qml`, which fails with "sailfish-qml: not found".
- The gdbserver install hint now includes `pkcon refresh`.
- Fix command names showing as "Sailfish: Sailfish: …" in the Command Palette: command titles no longer repeat the `Sailfish` category prefix.

## v0.1.2

- Warn when a project path contains whitespace (including a trailing space in a folder name), which breaks sfdk's build engine with a confusing "Cannot find real …" error. The warning shows in the task terminal, and as a notification for Run and Debug.
- Signed builds resolve `sailfish.build.signingUser` before calling sfdk: a name matching one GPG key is pinned to its fingerprint, and a name matching none or several keys stops with a clear message, instead of failing inside the build engine's key import. gpg matches names as substrings, so `Jane Doe` also matches `Jane Doe Dev`.
- `Sailfish: Set Up Package Signing` command: pick a GPG key, or create one from VS Code input boxes for name, email and passphrase, and fill in the `sailfish.build.sign*` settings for the project.

## v0.1.1

- Optional RPM signing: `sailfish.build.sign` adds `--sign` to the build, deploy, run and package tasks, with `sailfish.build.signingUser` and `sailfish.build.signingPassphraseFile` passed to sfdk as session options.
- Require Node.js 22 or newer to build from source, drop `--allow-missing-repository` from the packaging command, and add the `repository` field to `package.json`.
- Update the CI workflow's actions to versions that run on Node.js 24.

## v0.1.0

- Detect the Sailfish SDK via `sailfish.sdkPath`, `SAILFISH_SDK_ROOT`, `~/SailfishOS` or `PATH`, gate on `sfdk --version`, and re-probe when `sailfish.sdkPath` changes.
- Detect Sailfish projects (`rpm/*.spec` + qmake/CMake) across single- and multi-root workspaces and keep them in sync with file changes.
- `Sailfish: New Project` wizard (`sfdk init`), Sailfish build-target selection and status bar, and `sfdk config --global` commands to set sfdk's own defaults.
- Build/deploy/run/package/check/clean tasks (task type `sailfish`) with streamed output, a build engine auto-start, and problem matchers for gcc/qmake/rpmbuild/rpmvalidator output.
- Devices & Emulators tree view (`sfdk device`/`emulator list`), start/stop/install commands, an SSH terminal command, and VirtualBox VM correlation for emulators.
- Devices & Emulators view gains an "SDK" group: SDK location/version, sfdk path, build engine state (with start/stop; refresh to see changes made elsewhere) and installed build targets, plus an install prompt when no SDK is found.
- Disable the Qt QML extension's `qmlls` language server per Sailfish project folder, since it requires Qt 6.8+ while Sailfish targets ship Qt 5.6 (`sailfish.qtqml.silenceQmlls`).
- Add 21 Silica QML snippets (`sfpage`, `sfdialog`, `sflistview`, `sfflickable`, `sfpulldown`, `sfpushup`, `sfcover`, `sfremorseitem`, `sfremorsepopup`, `sfbutton`, `sftextfield`, `sfswitch`, `sfslider`, `sfcombobox`, `sfsectionheader`, `sfdetailitem`, `sfbusy`, `sfviewplaceholder`, `sfappwindow`, `sfattached`, `sfnotification`).
- Add a "Get started with Sailfish OS" walkthrough covering SDK setup, project creation, target selection, the emulator and build/deploy/run.
